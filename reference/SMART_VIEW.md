# Smart View

`#view [name]` opens a **structure** or an **API** as a table (data sources are on hold, see below). `#view` alone asks which one (the list shows only what the signed-in person may open).
Code: `chat-app/features/smartView/` (`smartViewEngine.js` pure logic, tested in `tests/frontend/smartView.test.mjs`; `smartViewSources.js` reads; `SmartView.jsx` the screen; `SmartViewModal.jsx` the full-screen dialog).

## What it does
Search, filter (type-aware conditions: text, number, date, yes/no), sort (up, down, off; blanks last), group (with counts and a total), totals (ids, years and codes are never added up), a chart (flat, from the grouped or filtered rows), choose columns, save a **view** (search + filters + sort + grouping + columns and their order and widths, kept on the server per person and source, plus views shared with everybody), refresh, **download CSV** (what is on screen; opens in Excel). A source with parameters asks for them first and remembers the last values.

## Where the rows come from (all through calls the app already makes, so nothing is seen that the person could not already see)
**For now the Smart view shows structures and APIs.** Axpert data sources and Connectum data sources are **on hold** until they are approved: they are not listed, cannot be set up (Configure), and cannot hold views. The switch is one list in each place (`SMART_VIEW_KINDS` in `smartViewAttrs.js`, `?KINDS` in `sd_smartview.erl`): add the kind back to both and nothing else has to change. The rows of the table below that name them (and the code that reads them) are kept for that day.

| Source | Calls |
|---|---|
| Structure | `ai.enterprise {what:"forms"}` for the forms and fields, `submissions.list {tstruct, fetch:true, withDetails:true}` for the records (up to 3,000, pages of 500), with who, when and status |
| Data source | `datasource.list`, `datasource.run {name, values, limit}` |
| API | `api.list`, `api.run {name, values, limit}` |
| List (from a Data Fetch API, i.e. what Axpert answered the last time it was asked) | `isource.list` (those with `entity:"api"`), `isource.table {name}` -> `{columns, rows, total, fetchedTs}` |

## A structure made in the builder
Any structure (one of Connectum's own, one an administrator made, or one a person made in the builder) opens as a table: one column for each field, the key field first, then the record's **By** and **Submitted**. **The record's number (No., key `#`) is not a column**: it stays in every row as data (a click on the row opens the record; the three dots, History, delete and the conversation button read it), but it is never shown, offered in Columns, filter, sort, group or totals, nor downloaded, and the search box does not match it (it is not on screen). An older saved view or definition that names it loads and ignores it. The server applies who may see which records (the structure's own rule and its fetch rule); the Smart view shows what it is sent. Code: `svStructure.js` (pure, tested in `smartViewStructure.test.mjs`), `loadStructure` in `smartViewSources.js`.

**External ID.** A record another system sent in through the published API with an `externalId` carries it (read only, on the record itself). A structure that has at least one such record among the rows read gets one more column, **External ID**, after **Submitted**: shown like the others, and filtered, searched, sorted and picked in Columns like them; a structure without any has no such column (no empty column anywhere). The same id is one line of the record cards (My data, With me, Team, the Inbox row): `External ID`, last, only when the record has one. Code: `svStructure.js`, `recordRows.js`, tested in `externalId.test.mjs`. In a data source (Fetch from Connectum and the joins) it is the built-in field `@externalId`, "External ID", beside `@id`, `@created` and `@by`.

| Field type | Shown as |
|---|---|
| `text` (also several lines), `email`, `url`, `mobile`, `fill`, `barcode`, `autogenerate` (the number the server made, `VIS-0001`) | the text that was saved |
| `text` with **rich** text | its words only: paragraphs and line breaks become spaces, entities are read, a script or style block is dropped (it is only ever drawn as text) |
| `number`, `wholenumber` | a number (right aligned, summed by KPI cards) |
| `date`, `slot` (a booked time) | a date; a booking also shows its time. `time` stays text (a time of day is not a date) |
| `payment` | what was asked, how, and whether it is paid: `INR 500 · UPI · Paid` (or `Pay later`) |
| `toggle` | yes / no (a yes/no filter) |
| `selection`, `list` (several choices joined), a status dropdown, a list of people | the name of what was chosen (`labels` of the record: a person's name, not the user name), else what was saved |
| `location` | the street address (else its coordinates) |
| `file` | file chips with the real names (see *Files inside the rows*); the preview opens a picture or a PDF |
| a grid section | one column with its rows on one line: `1. Pallet, 4, photo.png; 2. Crate, 8` (the names of the files in a row stand for them) |

`withDetails: true` on `submissions.list` makes the server add `files` (name, type, size of each file field, also in grid rows) and `labels` to each record; without it nothing changes (older callers). A table **follows its records**: the `submissions_changed`, `submission_approved`, `submission_rejected` and `ticket_assigned` events of its structure (and a reconnect) read it again quietly: no spinner, the scroll stays, only the newest answer lands. The list of sources follows `tstructs_changed` the same way: a structure made in the builder appears, one that was changed is read again only when its fields changed, and one that was removed is said so in words and the window returns to the Overview. Deleting a structure or an API also deletes its set-up and shared views.

**Hidden fields are not in the Smart view.** A field marked hidden in the builder (and the four hidden fields a status keeps: latest completion, comments, files and hours) is not a column, a card, a chart or a filter of a structure's Smart view, for anyone, the structure's creator and administrators included: the server leaves it out of the forms list the Smart view is drawn from (`ai.enterprise {what:"forms"}`). The form's own definition (`tstruct.get`) and its records still hold it. Tested by `connectum_ai_enterprise_test.mjs` and `connectum_smartview_test.mjs`.

**How every field type is tested.** (1) `tests/frontend/smartViewStructure.test.mjs` builds a structure with every builder field type (`EVERY`) and the values the server really stores for each (probed from a real backend), and checks each cell, an empty record, hostile text and speed; `smartViewApiValues.test.mjs` does the same for every kind of JSON value an API can send. (2) `connectum_smartview_test.mjs` (section *EVERY kind of builder field*) saves a structure with every field type through the builder's own call, a record with all of them filled (a real uploaded file, a booking time from real working hours), and reads back what the Smart view receives (`submissions.list` with `withDetails`, and `ai.enterprise`). (3) `tools/ui-audit/smartview-fields.e2e.mjs` does it as a person would, in Chrome: it makes an organisation, builds that structure, adds records with a picture, a PDF, a text file and an HTML page called `.png`, serves a sample API with every kind of value, types `#view <name>`, clicks Expand and checks the table, the previews, dark mode and a phone (`SHOTS=<folder>` keeps pictures). Run it with a backend started with `CONNECTUM_API_ALLOW_PRIVATE=1` and `npx vite --port 5799`.

## An API
An API answers with rows of any JSON. Each column's kind is read from its values (up to 200): numbers (also `"1,200.50"`, `"45%"`, `"$1,200"`), dates and date-times (also a timestamp), yes/no (a JSON boolean or the text `true` / `false`), files (see *Files inside the rows*), lists and nested objects (a short line: `a, b`, `a: 1 · b: 1 field`, `2 items`), and text for everything else. A long number, a phone number or a code with a leading zero is text, never rounded. Markup in a value is data: it is drawn as text. No value ever shows as `undefined`, `null` or `[object Object]`; nothing is shown as a dash. The server cuts an answer at 500 rows and the screen says so; an error, an answer that is not JSON, or one that takes longer than the API's time limit is said in words with *Try again*. The server sends the columns in alphabetical order; **Configure** puts them in the order a person wants.

## KPI cards, chart and list
On the inbox lists (**Visualize**) and nowhere else, the cards are worked out from the rows. A structure, data source or API shows only the cards and charts set up for it (see *Smart view attributes* below), none until then. The inbox lists have, above the table, one **KPI card** per number, on the app's own stat-card standard (a card, a hairline, a 4px top bar, a rounded-square icon): the theme's coral for a plain number, amber for waiting, green for done, red for declined, no other hues and no grey fills; the Overview's totals and the downloads use the same card (rows, groups, each total with its average, the most common value). The **Chart** button opens a full-width band between the KPI cards and the table (never a column at the side), with the chart on the left and the ranked list on the right; the downloads (PDF, PowerPoint, image) use the same arrangement. It has the chart (donut or bars) and a **ranked list** of the top values of the same column, with counts and shares (`kpiCards`, `topValues` in the engine).

## The list of sources can be folded
The full screen has a list of structures and APIs on the left. The **menu button** at the left of its header folds the list (and shows it again); Space and Enter work on it, and it says which it will do ("Hide the list of sources" / "Show the list of sources"). **Expand** on the card opens the full screen on the source that was on the card with the **list folded**, so only that source shows, across the whole width; the header names it. A plain `#view` (no source chosen) opens with the list and the Overview. On a phone the list is a row above the table and folds the same way. The folding rule is `opensFolded` in `svLayout.js` (tested); a saved list width (`connectum.sv.navw`) applies only on a wide screen. The sliding highlight of the list keeps its place while the list is folded (`GlassLens.jsx` does not measure a hidden list).

## Smart view attributes: what a data source shows (Customize)
A **structure or an API** can be *set up* once so that its Smart view shows exactly what was decided: which columns, with which captions, which of them are links, which KPI cards and which charts. A source nobody set up is a **plain table**: no KPI cards and no charts, nothing worked out for it (the menu says "No KPI" and "No charts"). Only the inbox lists work out their own. Code: `smartViewAttrs.js` (the pure part), `SvConfigure.jsx` (the screen), `sd_smartview.erl` (storage and checks), tests `smartViewAttrs.test.mjs` and `connectum_smartview_test.mjs`.

**Who:** anyone who may open the source reads the set-up (`smartview.attrs`: names of columns, never data). **Options > Customize** shows only to people holding the permission **Set up Smart views** (`smartview.configure`; administrators always; an administrator can give it to people, roles or designations under Permissions). The server decides.

**Customize** (it was called Configure) opens "Customize View" over the view. **For now it offers Cards and Charts only**: the Columns and Links lists are switched off in `SvConfigure.jsx` (commented in `TABS`, their editors are kept) and come back by putting those two lines back. What was saved for columns and links before keeps working. A card or a chart needs its columns listed: with Columns off, they are listed from the source itself when a card or chart is saved. The grids were (add, delete the ticked lines):
- **Metadata**: Field name (a drop down of the source's own columns), Caption, Data type (Character, Numeric, Date, Boolean), **Hide** (the column stays in the data for KPIs and links but is not shown, and is not offered in Columns), **Is Keyfield?** (key icon), **Apply filter** (the column gets a line in the filter panel), **Source form** and **Source field** (the column takes its values from another form: it is chosen from a list in the filter). **Fill grid** adds one line for each column of the source that is not there yet (what is already there is kept). The metadata decides which columns exist: a source column that is not listed is not shown.
- **Hyperlinks**: Field name, type (**Load structure** or **Load from API**), target, **mappings** (a column of this view on the left, the target's field on the right; up to ten), **Inline**. Clicking a link cell opens the target over this view as the one record the mapping finds (a structure's record as a card of fields; another Smart view filtered). An empty cell opens nothing; a mapping to a field the target lacks is said in words.
- **KPIs**: Caption, Aggregate function (Sum, Average, Minimum, Maximum, Count), Aggregate column. Counting needs no column. The cards follow the search and filters.
- **Charts**: Caption, Chart (line, bar, stacked-bar, column, stacked-column, stacked-percentage-column, area, pie, semi-donut, donut, stacked-group-column, scatter-plot, funnel), Group by, Aggregate function and column. Each card says what it shows ("SUM Net by Channel"), has a tooltip on every mark, can be made big, and the row scrolls sideways (arrows, arrow keys, swipe). Biggest first; a date column in date order; at most 40 groups, the card says when more were left out. Charts follow the search and filters.

The screen checks each line before saving ("Charts, line 2: choose what to group by"); the server checks again. A definition that names a column the source no longer has is skipped, so a changed source never breaks the view. **Remove set-up** returns the source to a plain table.

## The options menu, views, filters and grouping
The **more (three dots)** menu: **Columns** ("Select Fields": search, Select all, Reset, at least one stays), **Group** (tick one or several columns: the first ticked is the outer group, with counts and totals at each level), **Create view** (a name, then a new tab beside Default View that starts as the plain list of the records: every column, no filter, group or sort; customize it and save it with the Save button; there is no "+" on the strip), **Remove view** (a saved view, asked first), **Hide KPI** / **Hide charts** (or "No KPI" / "No charts" when there are none), **Configure**. A view stores the search, filters, sort, grouping, columns left out, **the order and widths of the columns** and whether the cards and charts show.

**Views live on the server**, so they follow a person to any device: a person's own views per source (up to 20 and the Default View), and **shared views** that a person who holds `smartview.configure` publishes for everybody who opens the source (**Share with everyone** in the menu; **Update shared view** and **Stop sharing** for configurers; others can **Save as my own view** from a shared one). Shared views are tabs with a group icon after the person's own. Views a person saved on a device with the older version move up to the server the first time the source is opened, and the local copy is removed. Sources that cannot be configured (the Inbox lists) keep their views on the device.

**Column layout.** Drag the grip on a header's right edge to change a column's width (64 to 800 px; the arrow keys change it by 16 px when the grip has focus; a double click gives the column its own width back). Drag a header onto another to move the column, or press **Alt + Left / Right** on a focused header. **Reset column layout** in the menu appears once a column was moved or resized, and the layout is kept in the views.
The **filter bar** ("Click here to Filter Data") opens a panel with one line for each column marked *Apply filter*: a list to choose from (several values) for a column from another form or one with few values, text (starts with, contains, is), a number range, a date range with presets (today, yesterday, this week, last 7 days, this month, last month, this year, custom), yes or no. What is applied shows as chips that each take their condition away. Sources without a set-up filter by every column.

## `#view` and `#inbox` are two things
**`#view <name>`** opens that structure straight away. Typing `#view ` suggests what you may open: the structures you made come first ("your structure", with its field count), then Connectum's own ("built-in structure"), then data sources, APIs and lists; typing letters narrows the list (names that start with them first). The same order is used in the Smart View's list and the Overview (`ai.enterprise` sends a `system` flag for the built-in ones).
**`#view`** alone is for looking at data: an **Overview** (a KPI card for every structure you can open: records, the last seven days, how they stand, when the last one came), then each structure, data source, API or list as a table with KPI cards, a chart and a ranked list.
**`#inbox`** (`HashInboxModal.jsx`) is a mailbox. Folders: **All** (what needs you; the window itself is still called the Inbox), **Tasks & tickets** (every open record with you, or raised by you, each opening to its own card with Send and Update status; see `RECORD_ACTIONS.md`), **Approvals**, **Reminders**, **Broadcast**. Direct messages stay in the notifications and chats, not here. **Broadcast** is company-wide news and announcements: only that folder shows them (never the Inbox, and they are not counted as "waiting for you"). Opening one marks it read; **Mark all read** clears the folder's count. The folder has two views, **Received** and **Sent** (`BroadcastSent.jsx`): Sent lists what this person broadcast, newest first, and each opens to when it went out, who it was for (branches, departments, designations, roles), how many people it reached and who (the first ten names; older broadcasts have none), and the message as written. It reads `broadcast.list` (`sample` holds the names, kept by the server since this change). The notifications themselves (the workspace feed and its bell) are unchanged and still hold every notification, tasks and approvals included. Where the messages come from is one switch, `localStorage.connectum_broadcast_source` (`chat-app/features/smartView/broadcasts.js`): `dummy` (the default) shows sample news, read marks kept in the browser; `live` shows the real announcements sent with `broadcast.send`, read from the workspace feed (`feed.list`, marked read with `feed.read`), so no server change is needed to wire them. Every message is a row. A waiting approval has **Approve** / **Decline** on the row (`req.respond`); a ticket or task opens to its own card with the actions its form allows (`status.update`). A cleared message slides out and the mailbox is read again; it also re-reads when a ticket, task or approval event arrives.
**The Inbox layout (this branch, not yet in `dev`).** There is no list of folders on the left any more. At the top of the records, in the middle, are four tabs: **All** (a small animated tray; everything that needs you: tickets and tasks, approvals, reminders; company broadcasts stay out of it, as before), **My data**, **Approvals**, **Reminders** and **Broadcast**, there is no Filter button; the **My data** tab opens a small list right under it with three scopes, **My All Data**, **With me** and **Team** (the tab then names the scope that is on) (With me and Team keep their four sub-filters as pills, and their records are drawn as cards four to a row like My data, each with a **tick box** (a bar shows how many are ticked, Select all, Clear and **Update status**: the ticked records move together to a status that every one of them offers, only those the server lets the person update, and a record that needs more than a status (completion, hours, comments or a file) is left for its own panel and counted as skipped), each ending with the record's own Send and Update status buttons and where it stands, as in My data (a card whose panel is open takes the whole row, with the record on the left and the panel on the right on a wide screen; only one record has a panel or History open at a time, opening another closes it; on a wide row Update status lays out the statuses across the top, completion beside hours and comments beside files, so it fits one screen); the server says what the person may do, so a structure without a Status field shows none); at the right end of the same row are the **Sort**, Refresh, the count and a **Search** box (the Visualize button was removed). Every record shows its date and time (the device's own format; the relative "2 h ago" is in its tooltip) and the list is newest first by default: what is unread is marked on its row, never lifted above newer mail. Each record row folds and unfolds (the arrow at its end).
The three **major** filters on records and the kinds of mail (My data, Approvals, Reminders and Broadcast are tabs; With me and Team are scopes of My data):
- **A form's approval request** (a leave, a purchase order: any structure with an approval step, `req.type` "submission") is drawn as the same card, in the Approvals tab and in the Approvals window: a tinted band ("Leave request from @asha on 17-Nov", the request number and time, and PENDING / APPROVED / REJECTED), the answers under it (dates written as dates), then History (inline) and the actions. The actions and who may use them are the existing ones, unchanged: Approve, Return and Decline only where the server says the person may answer (`canRespond`), otherwise "Waiting for their answer"; a reason is asked where the structure needs one. No Send: a record that waits for approval cannot be sent until it is answered. Other requests (sign-ups, invitations) keep their own card.
- **The numbers.** Every tab says how many records it holds (a quiet number): All (what the All tab lists), My data (its scope: My All Data, With me or Team), Reminders; Approvals and Broadcast keep their blue number (what is waiting for the person / unread). The count beside the search is what is listed now, "109 of 198 messages" while more is still to be read, and the All tab has a **Show more** under its list for the rest of what is with the person (100 at a time). The server counts every record it holds for the person, including a few it does not send (a form they may no longer read), so a number with "of" can be a little high until the rest is read; then it is exactly what is listed.
- **Lazy loading (every list):** the server is asked for **100 records at a time** (My All Data, With me, Created by me, Assigned to me and the Team lists; the Team lists go on from the position the server gives). The first cards are drawn 24 at a time; when the foot of the list is reached and all that was read is drawn, the next 100 are read. A search reads the rest of the list that is on first (200 at a time, up to 5,000).
- **The record card** (the same in My All Data, With me and Team): a tinted band with the structure and number, who raised it and when, and where it stands now (the live status chip); under it the name and value of each answer (an empty one is left out; the answers scroll inside at a medium height); along the foot the record's actions (Send, Update status, History, Edit, Delete: only what the server and the structure's own permissions allow). It is one component, `smartView/RecordFrame.jsx`. Every card has the same fixed height (424px, `--rc-height`) so a row of cards is even: the answers scroll inside and the actions stay at the foot; a card with its Send or Update status panel or its History open is as tall as it needs to be. The approval cards of the Inbox are at least that tall, and a row of them is as tall as its tallest. The heading is worded as the design sheet has it (`smartView/cardTitle.js`): a record somebody else raised reads "Task from @asha on 14-Oct", one the person made "Created sales order on 14-Nov-2026"; the status is the chip beside it ("Waiting for approval" while the form's approval step has not answered). The answers come in the order of the structure's fields and are written the Smart View's way (dates, amounts), read once from `ai.enterprise` (what "forms") by `smartView/recordRows.js`; a field hidden in the structure is left out. `tools/inbox-ui-seed.mjs` makes the five structures of the design sheet (Task, Leave request, Sales order, Maintenance reminder, Purchase order) with sample records in a local organisation.
- **My data**: the records the person made, **by structure** (one list of cards, **four to a row** (three, two or one on narrower screens), no headings or groups, in the order of the Sort menu), each record the same card as My Submissions with its answers as name and value pairs, at a medium height (the answers scroll inside). Every card has a **tick box** (multi-select): a bar shows how many are ticked, Select all, Clear and **Delete** (only what the person may delete: the same rule as a card's Delete; the server asks again). Cards are drawn 24 at a time as the list is scrolled and the records are read from the server a page of 100 at a time as the list is scrolled to its end, so hundreds of records stay quick; a search reads the rest first (up to 5,000). Ordered by the Sort menu.
- **With me**, with a **sub-filter dropdown** under the top row, on the left, that holds four choices: **Pending with me** (`records.mine as:"with"`), **Created by me** (`as:"raised"`: made by the person, now with someone else or waiting), **Assigned to me** (the open part of `as:"involved"`: given to or shared with them) and **Completed by me** (the finished part of `involved` that the person acted on last: `actedBy`).
- **Team**, with **Pending with team**, **Created by team**, **Assigned to team** and **Completed by team**: cuts of `records.mine as:"team"` by how each record is tied to the team (`team.via`: holder or shared = pending with team, raised = created by team, sent or shared = assigned to team) and, for completed, `as:"team", done:true` (the finished records of the direct reports, by the same checks).
- Mail: **Approvals**, **Reminders**, **Broadcast**. **All has no chips: it is everything** (records, approvals and reminders together, newest first); Approvals has chips for where each one stands, Reminders for today and later / earlier.
The menu is the same for everybody; Team is empty, and says so, for a person nobody reports to. **No permission was added**: every list is what the server sends under the structure's own rules (who may read a record, `hideFromManagers`, who reports to whom), and only a record of a structure that has a status field is listed (the status is what pending and completed mean). Under the top row, on the left, is one row of **dropdowns**: the sub-filter of the section (the four of With me or Team; Received / Sent in Broadcast; status in Approvals; today and later / earlier in Reminders; none in All and My data) and a **Sort** that works in every list: **Latest** (the default), **Oldest**, **Ascending (A to Z)** and **Descending (Z to A)** by the title of the record. There are no chips and no per-structure row; the search finds a structure by its name. The search finds every word typed, in any order, whatever the case or accents, in everything: while words are typed the rest of the records with the person is read (pages of 200, up to 5,000), and approvals are found by their form, what was filled in and who asked. Real approval requests carry their details under `data` (`caption`, `message`, `summary`, `tstruct`) and the time as `createdTs`; reminders are feed notifications of the category `reminders` (the text is the `message`). **`#tasks` (and `#task`, `#todo`) and the Inbox's My tasks view were removed on this branch.** Code: `inboxFilters.js` (pure, `tests/frontend/inboxFilters.test.mjs`), `HashInboxModal.jsx`.

**From the inbox to the Smart View:** **Visualize** (on the folder, and on a row) opens the Smart View on your Tasks & tickets, Approvals or Reminders as KPI cards (rows, one per status such as Open / In progress / Waiting / Approved, totals, top value), a chart and a list. Only a Smart View opened this way offers those message lists ("Your messages"); plain `#view` does not. The Tasks & tickets table there lists the same records (form, status, who it is with, completion).

## Files inside the rows (an API, or any source)

A column whose values are files is shown as **file chips**, not as text. Nothing has to be set up: the column is recognised from its values (`inferType` in `smartViewEngine.js` asks `isFileColumn`), and Configure can also declare a column of type **File**. Code: `svFiles.js` (pure: what is a file, what may be opened), `SvFiles.jsx` (the chips and the preview), `fetchFileBlob` in `services/connectumFiles.js`; tests `smartViewFiles.test.mjs`.

- **What is a file:** a link ending in a known file type; a link to one of Connectum's own files (`/api/sd/files/<24 hex characters>`); `{fileId}`; a small picture written into the value (`data:image/png;base64,...`, at most 2,000,000 characters); an object with `url` (or `href`, `link`, `src`, `path`), `name` and `mime` (a declared file needs no extension); a list of these, JSON text of these, or links separated by a new line, `;` or `|`. At most 20 per cell. A column is a file column only when **every** filled value is a file; one plain value makes it an ordinary column.

- **What is never a file:** `javascript:`, `data:` pages, `blob:`, `file:`, `//host` links, links with spaces or control characters, an ordinary page link with no file type.

- **The cell:** one chip with the file's name (icon by kind) and `+N` for the others (hover lists their names). Click opens the preview.

- **The preview** (themed dialog, Previous / Next, arrow keys, Escape): pictures and PDFs are drawn in the dialog; any other file offers **Open in a new tab** (a link on the web) or **Download** (a Connectum file or a picture written into the value). Only `https`, paths on this site, small pictures in the value and Connectum files are drawn inline; plain `http` links and SVG pictures are not (SVG may carry script). A Connectum file is fetched with the person's sign-in and shown from memory; because the server sends every file as a download with no type, **what it is comes from its first bytes** (`sniffKind`: PNG, JPEG, GIF, WebP, PDF), never from its name.

- **Search, filter, download:** a file column is searched and filtered by name and link (the text operations); CSV, TSV and Excel carry the links, not the names; charts skip it.



## Changing records: the structure's own rules
The Smart view adds no permission of its own (the only one is `smartview.configure`, a default look for everyone). What a person may do with a structure's records is decided by the structure, and the screen follows what the server says:
- **Change:** each record the server sends carries `canEdit` (`sd_config:may_edit/2`): its author, or whoever the data-access rules let change it, while it is not locked for approval and its structure is a normal one. Only such a record opens on a click of its row, and it opens in the structure's own form (the Smart View closes and the host screen opens that form, filled with the record: `onEditRecord`, the same form as Edit in My submissions); the others are plain. `submissions.update` asks the same questions again.
- **Delete:** in the structure's own screens: anybody may delete their own, and the person who **created** a structure may delete any record of it.
- **Whose records a table holds.** Always the structure's own rules: the server lists only what the person may open, and the Smart View asks for nothing more. A structure's table shows what the person made; what their **direct reports** hold, were sent or made (the server's team rule, read only, `docs/CONNECTUM_API.md` *Team records*: `submissions.list` already includes them for a reporting manager, and leaves out a form that switched on `hideFromManagers`); and what **names the person**: records sent to them, shared with them, assigned to them or that they acted on, read with the existing `records.mine` (`with` and `involved`) and merged by number (`taggedIn` in `smartViewSources.js`). A record that is not theirs can be read, never edited (`canEdit` comes only with the structure's own list). Tasks & tickets adds the open records of every structure with a status that the person may see (`loadVisibleOpen`: the same list call, so the same rules, the team's included). A table opens as a **table**, also when it holds one row (a single card is only for a Get API or a link's target). For a structure with a status, the columns are: No., By, Submitted, **Approval** (recorded, waiting, declined), the status field, **With**, **Progress**, then the other fields (what the status's updates said, `<field>_comments` and so on, is not a column); the opened row (the history button) starts with Status, With, Progress and Raised by.
- **Team tab (Inbox → My submissions, `SubmissionsModal.jsx`).** A person with direct reports (`hasReports` on their own object) gets **Team (n)** beside Mine and With me; nobody else sees the tab. It reads `records.mine {as: "team"}` in steps, continuing from `next` (never `offset + items`), once for each record, newest first. Each card is **read only** (no Edit, Delete, Send, Update status or approval) and says "With @x" or "Sent to @x" from `team.via` next to "Raised by @y". It refreshes on `submissions_changed` and on a reconnect.
- **No origin pill.** The footer no longer shows where the data came from ("Your records"): the refresh icon is the way to read it again.
- **Hidden fields.** A field the builder hid (`hidden`) is not a column: `ai.enterprise` leaves it out, so a table never shows one by default. **Anybody who can open the table** can turn on **Show hidden fields** for themselves inside **Columns** (the Select Fields dialog, under the search box; off until they do): the form's definition is read once and the table is read again with those columns, which join the list ticked; unticking the switch takes them away. The fields a status keeps are never added (they are the Progress column). It lasts while the view is open. The form builder's own rule for hidden fields (Studio's list of a structure's records) is separate and unchanged.
- **Where a record opens.** Every record of a structure (and every row of Tasks & tickets) opens on a click of its row, and where follows the server's word on this person: **in the structure's own form** when they may change it (`canEdit`), otherwise **in the same form to read** (titled "View …": every field locked, filled with the record, only **Close**; nothing to save or delete). The Smart view closes and the screen that hosts it opens that form (`onEditRecord`, `onViewRecord`, `onAddRecord`; the form takes `editing.viewOnly`).
- **Inbox.** A record in the Inbox has no "Visualize in Smart View" button any more; the folder keeps its own **Visualize** button.
- **Add and delete** (a structure's table only). A **+** button in the footer takes the person to the structure's own form, empty, to add a record (the Smart View has no form of its own: it closes and the screen that hosts it opens the form the rest of the app uses; `onAddRecord`); it shows when the structure says `canAdd` (the "Enter records" rule, `ai.enterprise`). Every row has a checkbox and the header has one for all, like a mailbox. A **bin icon** in the footer is always there but works only once records are ticked (it is greyed out until then); it asks first and deletes one record at a time with the existing `submissions.delete` (at most 200 in one go). Who may delete is the structure's own rule (`submissions.delete`): the author of the record, or the owner of the structure. The server sends no flag for it, so the table offers Delete only for those (a report's record a manager reads is never theirs to delete); ticked records the person may not delete stay and are counted in the question. The server asks the rule again on every delete and refuses in its own words (a record waiting for approval or approved, for one). Code: `svDelete.js`.
- **Share is hidden since 17 Nov 2026** (the owner's decision), behind ONE switch: `SMART_VIEW_SHARE_ENABLED` in `chat-app/features/smartView/svShareSwitch.js` (`false`). To turn it on again, set it to `true`: nothing else changes. Nothing was deleted: `SvShare.jsx`, the server commands (`smartview.targets`, `.share`, `.shares`, `.unshare`, `.view.unshare`; the server does **not** check the switch) and their tests stay. A view somebody shared **before** still shows as a tab (group icon) to the people it was shared with, so nobody loses access; what is hidden is every control that creates or changes a share. Every surface that was looked at:

  | Surface | Decision |
  |---|---|
  | Options menu (three dots): **Share** (`person_add`, `sv-opt-share`) | hidden (`shareMenuItems`) |
  | Options menu: **Stop sharing this view** (`group_remove`, `sv-opt-unshare`) | hidden (`shareMenuItems`); a person who shared a view cannot take it back from the UI until the switch is on |
  | The Share dialog (`SvShare`: Share with, Shared with, Stop sharing with) | not reachable: mounted only for `dialog === "share"` and `shareDialogAllowed()` |
  | Shared tabs (group icon, "Shared with everybody who opens this") | **left**: existing data, read access of the people it was shared with |
  | "Save as my own view" on a shared view | left (copies a view, creates no share) |
  | "Save this file" dialog note ("...and can be shared") | the words are left out (`saveFileNote`) |
  | Overview / list of sources (`SmartViewModal`), Inbox (`HashInboxModal`, `WorkCards`, `inboxFilters`: "Assigned to me" is records, not views) | nothing to hide; checked in a browser |
  | Keyboard shortcuts, `#view` / `#inbox` routes, notifications | no share shortcut, route or notification exists in the web app |
  | `publishView` / `unpublishView` (admin publish of a view for everybody) | no screen calls them; left in `smartViewSources.js` |
  | `WhoCanUse` (Links, Plugins, AI: "Who can use it", Change) | **left**: not Smart View |
  | form-studio, plugins | no Smart View share entry |

- **Share** (the three dots) shares a *view* (its filters, columns, grouping) of a structure or an API with people and groups: it shows to them as a tab. No new permission: it follows the structure's own rules. A person can share only what they can open themselves (`sd_smartview:may_open/3`: the structure is one the app lists for them, less the ones its own `restricted` rule keeps from them), and the other person gets the tab only if *they* can open it; otherwise the server sends no view to them. The sharer is told who cannot (`noAccess` in the answer, and "Cannot open this structure" in the Shared with list). A share gives nobody a record: what they see, add or change is the structure's rules. There are no Read / Add checkboxes.

## History of a record
**Back to the Smart View.** A record opened from the Smart View (the **+** to add one, a row to change it, or to look at it) opens its form; closing the form (Cancel, the cross, or after saving) brings the person back to the Smart View on the same structure. This is only for what was opened from the Smart View: a form opened from a chat, the Inbox or the menu closes to where it was. It is done in the screen's dialog layer (`ChatModals.jsx`) and changes nothing on the server.

**Columns behave like a spreadsheet's.** A column opens as wide as its heading and the longest text in the first 200 rows need (never narrower than a floor for its kind: 90px for numbers and yes/no, 150px for dates, 120px for text; never wider than 320px when it opens), and the window's spare width is shared by the columns (text takes most). A long text is cut with an ellipsis in its cell and shown whole in the cell's tooltip. The person can **drag** a column's right edge to resize it, or **double-click the edge to fit the column to its text** (up to 600px), and **Reset column layout** (the three dots) puts every column back. Widths and order are kept in the person's views. **My team (left list).** Under **Overview**, a manager has a fixed entry, **My team**: a table of the records of the structures that have a status or Send switched on that were **assigned** to the people reporting to them: sent or shared to them, or held by them although somebody else made it. What a team member made and still holds for themselves is not shown (`assignedToTeam` in `inboxFilters.js`; the server list has it as `via` "raised" only). (The reporting-manager line the server keeps, read through `records.mine` as `team`, open and finished, a page of 200 at a time up to 1,000). It is read only: a record's three dots offer what the server allows (nothing a manager may not do to a team member's record), and a record is opened by the structure's own rules. The entry shows only to somebody who has people reporting to them (the server's `reports` count), and the Find box finds it by name. Columns: Title, Form, Status, Progress, With, Raised by, Raised.

**Large text, like a spreadsheet.** A long text is cut with an ellipsis and shown whole in the cell's tooltip. To read it in the table: **drag the bottom edge of a record down** to make it taller (its texts wrap and show whole; drag up to make it shorter; never shorter than the usual row), **double-click that edge** (or press Enter on it) to fit the record to its longest text, or turn on **Wrap text** in the options (the three dots) to fit every record at once (the height is measured from what is drawn, so the whole text is shown; only a value taller than 6,000px is cut); **Reset column and record sizes** puts it all back. A column is made wider or narrower the same way by its right edge (drag right to widen, left to narrow; double-click to fit). Record heights and Wrap text last while the table is open (they are not saved in a view; the column widths are).

A field added or changed in the builder appears in the table and in **Columns** (Select Fields) without reloading: the Smart View follows the structure's definition. This also holds for a structure that has a **set-up** (Customize, the columns an administrator listed): a field added after the set-up was made is shown after the listed columns (and can be filtered); to keep a field off the table, **Hide** it in the set-up (removing its line does not, because the field is still the structure's). The status columns stay off by default whatever the set-up lists.

**KPI card widths.** Each KPI card is **at least 240px and at most 440px wide** (`--sv-kpi-min`, `--sv-kpi-max`, and the gap `--sv-kpi-gap` of 16px, in `smartView.css`). The cards of a row share it equally: as the window grows they widen together up to 440px and more of them fit in a row; as it shrinks they narrow together to 240px and the rest wrap to the next row (the last row keeps the same width); below 640px (a phone) every card takes the whole width. The strip is no wider than its cards can be (`--kpis` set from the number of cards), so one or two cards never stretch across a wide screen. Any number of cards works the same way.

**One heading, minimal columns.** The window's header names the source and says how many rows and how fresh ("Structure · 40 rows · updated just now"); the table has no second title. A structure's table opens on **its own layout, in the order the builder put its fields** (the key first, then the fields), and, **after all of them, at the end**, the record's own columns: **By** (shown only when more than one person made the records) and **Submitted**. **The status is not a column**: a structure with a status dropdown shows the **three dots** on each record (Send, Update status, History: where it stands and changing it), and the status, the approval state, who the record is **With** and its **Progress** are left out of the table by default. A person who wants them turns them on in **Columns** in a view of their own (kept in that view as "+Name" in its hidden list); a structure without a status dropdown has no dots. The bar under the table (views, filter, tools) is **fixed at the foot of the window**: the cards and charts above scroll away behind it, it does not. **Download** (the arrow in the bar under the table) offers Excel, **CSV**, Google Sheets, PDF, PowerPoint and Image of what the table shows now (its filters, sort and columns).

A structure that has a status dropdown, and Tasks & tickets, show the **three dots** in front of each record (inside the first column's cell, before its first real field; a table with no column at all gives them a cell of their own). They offer what the server lets the person do with the record (**Send**, **Update status**: the record's own forms, rules and permissions) and its **History**. Each opens as a **pop-up** over the Smart View, one at a time (Escape, the cross or a click outside closes it): Send and Update status as the record's form (statuses across the top, completion beside hours, comments beside files; saving reads the table again), History as the app's Answers and History window (who did what and when: made, sent, status updated, changed, approved). Read with `submission.history {id}`: whoever may open the record may read it. There is no "My history" source and no `#view myhistory`.

## Open your own Excel or CSV file, and save it
A person can open a spreadsheet from their own device as a table with no setup: **Open an Excel or CSV file** (a drop zone above the list of sources). Code: `svFileSource.js` (pure) and `SvOpenFile.jsx`.
- **Read in the browser.** `.xlsx` or `.csv` (comma, semicolon or tab; a BOM is fine), the first sheet, the first non-empty row as the header, up to 20 MB and 50,000 rows. Nothing is sent to the server until the person presses **Save**. An empty header becomes "Column N", a repeated one gets a number, a column with no header and no values is dropped.
- **A plain list.** An opened file (and the saved file) shows its rows only: **no default KPI cards or charts**. The person adds cards and charts in Customize view if they want them. (Only the inbox lists work theirs out from the rows.)
- **Everything the table offers:** search, filters, sort, grouping, columns, and **Download** (Excel, CSV, Google Sheets, PDF, PowerPoint, image). Customize view works for the file too, privately.
- **Save.** A small **Save** icon in the footer (next to Refresh and Download, only for a spreadsheet file: nothing else has it) asks for a name and keeps the file in Redis as a **structure the person owns** (`smartview.sheet.save`, `sd_svsheet.erl`): a field for each column (number or date only when all its values read that way; phone numbers and codes with a leading zero stay text) and a record for each row (up to 2,000 rows and 60 columns; a row the structure refuses is counted as not saved). Nothing is saved until it is pressed. It is listed on the left under **Your files** (right under History, at once), opens with `#view <name>`, keeps the person's saved views and Customize set-up, and can be shared like any structure (below). The window moves to it.
- **Delete.** Only for **Your files** (a file the person saved themselves, never a structure made in the builder, nor a file someone shared with them): a delete icon on the file in the left list (it appears on hover or focus) and **Delete file** in the three dots menu. It asks first, then removes **everything of it from Redis**: every row (including rows people it was shared with added), the structure and its sharing, everybody's saved views and set-up of it, and its record history (that history holds the file's old and new values; every other structure's history is kept as always). `smartview.sheet.delete`, `sd_svsheet:delete/2`, `sd_history:purge_structure/1`.
- Until it is saved the footer says "Your file" and the data is gone when the window closes. Not an Excel file, an old `.xls`, an empty sheet and a too-big file are refused in plain words.

## Changing your own records
A member can change their own records in the structure's own form: clicking a record opens it there (only a record the server says they may change). What the structure's own rules allow decides the rest (a locked record, someone else's record, the data-access rules). The Smart view has no button that adds a record; records are made in the structure's own screens.

## Files in a cell: preview
A file attached to a record opens in a preview from its chip. Pictures and PDFs are drawn. A **spreadsheet** (.csv, .tsv, .xlsx) is read in the browser and drawn as a table (the first 200 rows), with **Open as a table**, which opens it in the Smart view as a table of its own (search, filters, charts, Save). A **text file** (.txt, .md, .json, .xml, .log, .yaml) shows its text (the first 200 KB), always as plain text, never as markup. An older .xls or .ods says so in words. Any other kind of file says it cannot be shown and offers Download. Only files kept by Connectum are read this way (a web link is opened in a new tab).

## Tasks and tickets (Inbox > Visualize)
**A structure's own status** (a dropdown with the status switch, made in the builder) is read from the structure's definition, never guessed from words: the server sends `status: { field, statuses, final }` with each structure (`sd_actions:public/1`) and each record's progress as `completion`. In a structure's table the status field is drawn as a pill (a final status is green, the others plain, the same `toneOf` the record cards use) and a **Progress** column (a bar) is added; Tasks & tickets colours each record from its own structure's definition (a record waiting for approval is amber). Structures show up in the list by themselves (`ai.enterprise`) and appear live when the builder saves one. Code: `svStatus.js`, `svStructure.js`, `workItems.js`.

One read-only source, **Tasks & tickets**, opened with the **Visualize** button of the Inbox's Tasks & tickets list (not with `#view`, and not in the left list). It is the same list the Inbox shows: the records of structures **made in the builder with a status dropdown**, each with its status and progress (`svWork.js`, `records.mine`):
- what is **with** the person now, what they **raised** and is still open, and for an **administrator** every open one in the organisation (`as: "all"`, `sd_actions:every_open/2`). A record is listed once even when it is in more than one of these. A record at a final status is no longer open.
- Columns: Title, Form, Status, Progress, With, Raised by, Raised. It follows task, ticket and approval events by itself. Both can be searched, filtered, sorted, grouped and downloaded, and a person keeps their own saved views of it in Redis.
- **Three dots:** the same as a structure's: Columns, Group, saved views, **Customize** (the person's own cards and charts: private, no default for everyone; until set up it shows the plain list). Saved views and set-up are kept in Redis under the source kind `work`.
- **One structure at a time:** in the Inbox's Tasks & tickets folder, picking one kind in the "All kinds" list changes the button to "Visualize <that structure>": it opens that structure's own Smart View (its records, the history button on each, the progress in it), found by name, so any structure with a status works with no setup. With "All kinds" it opens this combined view.
- A status is changed where the record is (the structure's own screens); this view only reads. The to-dos of the separate Tasks feature are not in it.

## Where saved views live
Every saved view (a person's own views of a structure, an API, or of the inbox lists Approvals, Tasks and Reminders, and the shared views) is kept on the server in Redis (`sd:svviews`, `sd:svshared`), never on the device, so it follows the person to any device. Views an older version kept in the browser are moved up once and then forgotten there. Only the last parameter values typed for an API are still remembered on the device.

## Download the cards, chart and list (PDF, PowerPoint, image)
**Download** has a second group, *Report with the cards, chart and list*: **PDF** (`.pdf`), **PowerPoint** (`.pptx`, one slide per page) and **Image** (`.png`, the summary page). Page 1 is the summary (KPI cards, the chart, a ranked list of another column); the next pages are the table as it is on screen (12 rows a page, up to 20 pages in a PDF and 6 slides in a deck; Excel has all rows). Pages are drawn on a canvas in the app's own look, in the light or the dark theme, whichever the app is in (`reportCanvas.js`) and packed with no library (`reportFiles.js`: a minimal PDF, a minimal .pptx zipped with fflate); tests in `tests/frontend/smartViewReport.test.mjs`.

## Built for speed
Only the rows in view are drawn (a window with 10 rows of margin; 2,000 rows keep about 30 in the page). Filtering, sorting and grouping are each worked out once per change (memoised), not on every scroll. Charts reuse the app's flat SVG charts: no chart library.

## Why this and not the other developer's `smartview-react`
That code is real React, but it is Axpert's Smart View: it signs in to the ARM API with a **hard-coded user and password**, reads Axpert "ADS" metadata, needs about 1.9 MB of Axpert/Bootstrap CSS, draws every row, and keeps about 35 pieces of state in one 600-line component; the README's virtualised TanStack Table is not what the code does (it is a plain table). Its ideas (saved views, grouping, KPIs and charts, download) are kept; the code is not.
**Not built (yet):** server-side paging beyond the first 500 rows of an API.

## Who sees a structure, and who may add to it
A structure is in a person's Smart view when they may enter records into it, may read its data, or see every record of it (see PERMISSIONS.md, "Seeing a form does not need Enter records"). The Smart view has no add button: records are made in the structure's own screens, where the server refuses an add from anyone who may not enter records.

**Several files in one cell.** A row of normal height shows the first file as a chip and the number of the others ("+4"; hover for all their names). When the record is made taller (drag its edge, double-click the edge, or Wrap text) every file is listed, one under the other, and a long list scrolls inside the cell. A single record shown as a card lists them all too (`FileChips` `all` in `SvFiles.jsx`).

**Word files in the preview.** A `.docx` opens in the file preview as its words (headings, paragraphs, list items and tables) as plain text, read in the browser from the file's bytes with fflate (`svDocx.js`; nothing of the file becomes markup, a zip that unpacks to more than 25 MB or a damaged file gets a plain message, and at most 3,000 paragraphs and tables are drawn). Older Word formats (.doc, .odt, .rtf) still offer Download only, with the reason written.

**Switched off for now:** opening an Excel or CSV file from the device (the "Open an Excel or CSV file" button of the list and the "Open as a table" button of the file preview) and the "My team" entry. Nothing is removed: the switches are `SHOW_OPEN_FILE` in `svSwitches.js` and `SHOW_MY_TEAM` in `SmartViewModal.jsx`; set one to `true` to bring the part back.

**Records you are linked to, and "I cannot view it".** A record the person made, was sent, or is named in (any field of people: assigned to, raised to, watcher ...) is theirs to read whole, even when they have no permission on its form (docs/PERMISSIONS.md, "A person linked to a record reads it"). It appears in the Inbox's My data lists and in the form's list like any other record. A form they may not open but are linked to a record of is in their list as **records only** (no adding) and opens with `#view <form>` as the list of those records; a form with no record linked to them is not in their list at all. A record they are **not** linked to is never listed; opening it by its number or a link says **I cannot view it.** (`SmartStructureModal.jsx` shows the server's sentence). Tests: `connectum_record_access_test`.

**Unsaved changes in a view.** If the screen differs from the view you are on (a filter, search, sort, grouping, hidden column, order or width changed; `differs` in `svViews.js`) and you click another view tab or choose **Create view**, a small dialog asks **Save your changes?** with **Cancel** (stay), **Don't save** (leave the change behind) and **Save changes** (save it into this view, or the Default View, then move on). A shared view offers no Save (readers keep their own copy: use Save as new view). Clicking the **Default View** tab always lights that tab, also when a Default View was saved (before, the saved Default had no lit tab). Closing the whole Smart View or its back arrow does not ask.

**Inbox > All.** The records that are with the person are drawn as the same cards as My data > With me, first, right under the filter bar; approvals (waiting for you or answered) and reminders are cards under them too (`MailCards.jsx`: a tinted band with the title, who it is from and when, a status chip, the details, and the same Approve, Decline and Return buttons along the foot, for everybody including administrators). Rows remain in the other folders (Approvals, Reminders, Broadcast). Code: `cardRows` / `listRows` in `HashInboxModal.jsx`. The filter pills (All, My data, Approvals, Reminders, Broadcast) sit in the header of the full Inbox window, a little to the right of its title (so they never scroll away); in the small Inbox card inside a conversation, which has no header, they are at the top of the card and stay there while it scrolls. The count, search and sort stay on top under them (`.hi-pane > .hi-top` is sticky in `hashInbox.css`; the pills are `pills` in `HashInboxModal.jsx`).

**Inbox filter button and panel.** A round button in the top bar of the Inbox, after Search (small and expanded, every section; `InboxFilterFab.jsx`), opens the Smart View's filter panel, drawn just under the bar (the `.svf-*` styles of `svDefined.css`, with Clear and Apply; nothing changes until Apply). It works on the section the Inbox is on (the top bar chooses it: there is no Show line). Lines, in this order: under the record views (Forms, Me, My Team, Timeline) **Form** (one or more forms), **Sort**, **Field** (a field by its name, across forms, with a control that follows its type as in the Smart View: a number or a date is a From / To range, a short list of answers is picked from, a yes/no is Yes or No, anything else is typed; `fieldInfo` and `matchesField` in `workItems.js`), then **Day** (Any time, Today, Last 7 days, Last 30 days, This year), **Date** (one calendar: the records of that day) and **Time** (a window of the day on a slider with two handles, half-hour steps; `TimeRangeSlider.jsx`). Sort offers Latest, Oldest, A to Z, Z to A and, over the record views, the statuses **Pending, Assigned, Completed** (only the records at that status, newest first; there is no separate Status line). Day and Time cut every list by the time of the record (`inTiming` in `inboxFilters.js`). The top bar is **All** (with a list: All, Approvals, Reminders, Broadcast), **Forms**, **Me**, **My Team** and **Timeline** (`LENSES`), as plain text: Me is the person's own records, My Team their direct reports', Forms and Timeline both; Timeline has a heading per day. A record card shows Send, Update status and History in a three-dot menu in the corner of its band; History and Send / Update status are never open together, and each has a small close button. Tests: `tests/frontend/inboxFilters.test.mjs`, `tests/frontend/workItems.test.mjs`.

**Card colours.** A card says two things with colour, for every form with no set-up (`recordTone.js`, tested by `recordTone.test.mjs`). The **band** is where the record stands for the person looking at it: **green** completed (a final status), **blue** assigned (open and with someone else: given to them, shared with them, handed on), **amber** pending (it is with the person, or with someone of their team, and waits for action), **violet** waiting for an approval that has not answered, **red** declined or gone wrong (Rejected, Declined, Blocked, Failed, Overdue, Cancelled). The **stripe** on the card's edge is how important it is, from a field named or captioned Priority, Severity, Urgency, Importance, Criticality or Risk: **High / Urgent / Critical red, Medium / Normal teal, Low / Minor grey**. Hovering the band says what the colour means. The cards of All that are not records have the colour of what they are: an approval is violet, a reminder teal, a broadcast indigo. The shades are medium ones (halfway between the pack tone's tint and tint-strong, with its strong ink). Amber is the one documented exception to the pack (docs/THEME.md, "The yellow exception").

**Inbox header.** The small Inbox and the expanded one have the same header, in three columns (`1fr auto 1fr`): the title at the left, the five items (All, Forms, Me, My Team, Timeline) exactly in the middle, and at the right the filter button, Refresh, the count, Search, Expand (the small one only) and Close, in that order. Search gives way first when there is little room; when the card or window is under 900px wide the items drop to a row under the title. There is no line under the title and no "N of M messages" text: each item has the number of records it holds beside it, in the same small badge as All (All, Forms, Me, My Team and Timeline; the numbers stay whichever section is on; the lists are read in pages, so a number with a + is at least that many, and anything over 1000 is shown as 1000+; `countText` in `inboxFilters.js`). Under the search box a small line says how many records there are in the section: "34 records" when all are shown, "12 of 34 records" when a filter or a search leaves some out, "131+ records" while the lists are not read to the end (only while the server's numbers have not arrived). The numbers come from the server (`records.counts`, exact up to 1000, a record in two lists counted once; `loadCounts` in `workItems.js`), so they match the real totals. **All is everything**: every record the person can see (the server's `all`, so never below Forms, Me, My Team or Timeline) plus the approvals, reminders and other mail that are not records, and its list holds all of them. **My Team is shown only to a reporting manager** (`reports` above 0); everyone else does not see it, and tagged records stay in Me. The small Inbox's cards fill the card in as many columns as fit (260px at least each), and a card under 560px wide keeps the title, filter, Refresh and Search on one row with the items scrolling sideways under them. The Involved and Team lists are read when the Inbox opens, for these numbers and for every filter.

**Card icons and buttons.** The tick box of a record card has a small icon inside it for what the record is (`recordKind.js`, tested by `recordKind.test.mjs`), read from the form's name by general words with no set-up: task, ticket (also issue, bug, incident, support), leave, expense (also claim, invoice, payment), order (also purchase, sales, vendor), meeting, visit (also site, travel), maintenance (also repair, service), file (also document, report), person (employee, customer, candidate), project, feedback; a record that is none of these has a plain record icon. A tick takes the icon's place while the card is ticked. The cards of All that are not records have their own: an approval, a reminder, a broadcast (in the same box, not tickable). The buttons of an approval card (Approve, Decline, Return) are plain text pinned at the bottom of the card, with no fill, outline or icon; only the details above them scroll. A card's title and by-line are at most two lines each (the whole text is the tooltip).

**Select Fields dialog.** **Select all** sits on one line with **Show hidden fields**, to its left. What "Show hidden fields" has to say (for example that the form has none) is written inside the dialog, under that line, because a message on the page behind a dialog is covered by it.

**Order of the columns.** In **Columns** (Select Fields) the columns appear in the table in the order they were ticked (a column that stays ticked keeps its place; one ticked later goes after the others; one unticked and ticked again goes last). Reset puts the table's own order back (`applyColumns` in `SmartView.jsx`).

**Look of the table and the bar.** The views are a plain strip of underlined tabs with no glass or background (the design pack's grooved pill for every `role="tablist"` is switched off for the views strip and the Customize tabs in `smartView.css`). **Save** is one icon button of the bar beside Refresh, Download and Search; it opens a small menu: for a structure or an API **Save view** (stores what the screen shows in the current view; on the Default View, what it opens on) and **Save as new view** (a name, then a tab); for a file opened from Excel or CSV **Save to my files** and **Save view**. The lines between records and columns and under the headings are the theme blue (`--color-primary` at 24%; 42% under the headings). The chart lines of Customize (Title, Chart, Group by, Calculate, Of the column) sit in one row on a wide dialog.

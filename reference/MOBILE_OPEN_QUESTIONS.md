# Every remaining question, answered (3 November 2026)

Each answer says where it was checked. "Built now" means it was added in this change and has a test.

## Attachments

1. **`GET /uploads/<name>`, no sign-in?** Intended as it works today: the protection is the random 48-hex name; there is no sign-in or membership check (`chat_web_upload:serve_upload`). No plan to change it. Treat the address as private.
2. **Files are never deleted?** Changed: a file uploaded after 3 November is removed when the last message showing it is deleted for everyone, edited out or purged (see the table above). A file from before, a profile picture, and an encrypted attachment are never removed.
3. **Optional `w`, `h`, `dur` in the tag?** Yes. The server never reads the tag, and the web parser (`chatMessages.js`) reads only `kind`, `name`, `size`, `url`, `type` and `e2e`: extra keys are ignored, so nothing breaks. Use `w` and `h` in pixels and `dur` in seconds (numbers). The web app does not use them yet.
4. **Allowed types, limits.** The list is fixed (see above): HEIC, mp3, csv, zip and old Office formats are `415`. The app's own limits are 8 MB (images, voice notes), 20 MB (documents) and 25 MB (video); the repo's nginx files now allow 27 MB for `/upload`, and a server gets it when its nginx file is updated and reloaded (until then 10 MB). A real limit above 25 MB would be a code change; none is planned.
5. **How does the web write the size string?** Base 1024. A file of **more than 1 048 576 bytes** is `"<n.n> MB"` with one decimal (`(bytes / 1048576).toFixed(1)`, for example `"1.2 MB"`); anything else is `"<n> KB"`, rounded, never less than 1 (`Math.max(1, Math.round(bytes / 1024))`, so a 100-byte file is `"1 KB"`). Source: `Composer.jsx`, `handleFileChange`. The tag's `size` is only a label; the server never checks it.
6. **Voice notes and video: exact tag fields.** The tag is `[ATTACHMENT:{"kind","name","size","url","type"[, "e2e":{"key","iv"}]}]` and nothing else; **the web app puts no duration or dimensions in the tag**. A voice note is `kind: "audio"`, `name: "Voice note (m:ss)"` (the duration only as text in the name, `m:ss` with the seconds padded to two digits), `type` the recorder's type without its codec part (`audio/webm`, `audio/ogg` or `audio/mp4`; the file is `voice-note-<time>.webm|ogg|m4a`), `size` as above. A video is `kind: "video"` (any `video/*`), `type` its own (`video/mp4`, `video/webm`, `video/quicktime`), no duration. `kind` is `image`, `video`, `audio` (any `audio/*`) or `file`. Examples in `e2e-attachment-vectors.json`.

## History sync (an older device showing the past)

* **A. May the server refuse `e2e.sync.put` for a target that is not late?** Yes, built (see the table above): `not_waiting`. The target must also be one of the person's own devices (`not_found` otherwise).
* **B. Is `e2e.sync.page` complete for conversations the phone never opened?** Yes. The conversations come from the server: every direct chat the person has (`dm_partners`) and every group they are a member of (`chat_groups:list_groups_for`), not from what a device opened. A group nobody has written in for months is still listed. What the person cleared stays cleared; messages deleted for everyone are left out; only end-to-end messages are returned.
* **Messages from before the person joined a group.** The server does not filter by join time, so they appear in the pages; a device has no box for them, so `rewrapEnvelope` fails with `not_for_this_device` and the client counts them as `skipped`. That is expected: skip them, do not treat it as an error.
* **Pagination stability.** The cursor is `{c, b, k}`: `k` names the conversation, `b` is the message id to continue below. **Built now:** a cursor with `k` finds the conversation again by name, so a conversation made or removed in the middle of a walk shifts nothing; when the named conversation is gone the walk continues at the next one. A cursor without `k` (the older form, `c` and `b`) still works as before. Messages are walked from the newest id downwards, so a message that arrives meanwhile (higher id) is not in the walk and already carries a box for the waiting device (it was registered before the message was sent); an edit keeps its id; a delete is simply not returned. **Return the cursor exactly as the last answer gave it.**
* **C. A recovery test vector.** It exists: `docs/e2e-test-vectors.json`, section `recovery` (the fixed `code`, `normalizedCode`, the recovery key `id`, the sealed `blob` `{salt, iv, ct}`, the HKDF `info` and the `aad`, the `plaintext` and `plaintextParsed` `{e, s}`, and `mustRefuse` cases, with `steps` in order).
* **D. `e2e.status` and "last seen".** Yes: only a call that passes `id` records "last seen" (`touch`, at most once an hour per device, so passing it on every status call costs nothing). A device not seen for **30 days** (`SYNC_RECENT_MS`; for a device never seen, the day it was added) is left out of `waiting` and `helpers`, and may be replaced when the person is at the 10-device limit.
* **Would you add an audit record of the approval?** Built now: **`e2e.sync.approved {device}`** (user level) records that the person approved on one of their devices for a waiting device: audit `e2e.history_approved` and `approvedTs` on the device; reply `{approved: true, device, ts}`. `not_found` for a device that is not the caller's, `not_waiting` for one that is not waiting, 60 per 10 minutes. It is **optional for the app and not a lock**: the server cannot tell an approval from the device's own call, so `put` does not require it.
* **Maximum WebSocket text frame.** The server accepts **262 144 bytes (256 KB)** per frame (`MAX_WS_FRAME_LEN`). A `put` of 400 boxes is about 90 to 100 KB, 500 about 120 KB: both fit; 400 is still the right batch. The repo's nginx file sets no frame limit for `/ws`; no proxy limit has been seen. Stay at 400.
* **Budgets per person or per device?** **Per person.** `put` is 400 calls and `page` 600 calls per 10 minutes for the whole person, so a backup (stage D) and a hand-on running at the same time share them. `e2e.devices` (the send path) has its own bucket of 600 per 10 minutes per person and does not draw from those.
* **A device with no socket when `done` happens.** Nothing is pushed to it: `e2e_devices_changed` goes only to the person's connected devices. The device finds out on its next sign-in or `e2e.status`. There is no "history ready" push (there is no push provider at all).
* **Label sanitising.** Already done at registration (see the table above); the label is trimmed and cut to 60 characters on the server, so you can trust the length.
* **Concurrent sessions.** Built (see the table above): a phone and a laptop at once. The sign-in hop is gone.
* **Does the feed item carry the device id?** Yes, `ref.deviceId` (see the table above).
* **A long-lived test token for the stand-in tool.** Sign the tool in as a laptop (no `client`) and keep the phone as `"client": "mobile"`: they no longer end each other. How long a session lasts is the server's `CONNECTUM_SESSION_TTL_SEC` (15 days by default); set it higher on a test server for a longer one.

## My Workspace feed and notifications

Everything here is in `WORKSPACE_FEED_MOBILE.md` and `feed-replies.json` (real replies, made by `tools/mobile/capture-feed-replies.mjs`); the points below are the ones that file did not state.

* **A. Real replies for each kind of feed item and for resolve, dismiss, clear.** In `feed-replies.json`: `kinds` (messages, submissions, approvals, reminders, security, api), `feed_list`, `feed_list_filtered`, `feed_summary`, `feed_read`, `feed_read_false`, `feed_read_all`, `feed_resolve`, `feed_resolve_all`, `feed_resolve_all_again` (nothing open), `feed_dismiss`, `feed_dismiss_again`, `feed_clear`, `feed_clear_again`, `notifications_summary`, `notifications_list`, `notifications_read`, and `cards_list` (non-empty).
* **Which fields are always there?** Per `WORKSPACE_FEED_MOBILE.md`: `id`, `category`, `title`, `message`, `ts`, `priority`, `severity`, `icon`, `read`, `resolved`, `resolvedTs`, `count` always; `actionType`/`actionLabel`, `chatId`/`chat`, `from`, `ref` only where the kind has them. `actionType` is a closed list (`open_chat`, `open_message`, `approvals`, `tickets`, `submissions`, `about_me`, `axpert`, `none`); treat anything else as `none`.
* **`feed.list` paging.** `before` is a `ts` and the comparison is strict, so two items of the same millisecond could be skipped. **Built now:** pass the last item's `id` as **`beforeId`** with `before` (its `ts`): items of that same millisecond are paged through once each, in the order the list shows them. `before` alone behaves as before. `hasMore` is always present.
* **Idempotent and safe to repeat after a dropped connection?** `feed.read` and `feed.resolve` (also `{all:true}`) are: repeating gives the same state. `feed.dismiss` the second time answers `not_found`: treat that as done. `feed.clear` repeated is `cleared: 0`. There is no `cid` on these (they change a flag, not create something), so queue them and replay.
* **Retention.** The newest **300** items per person are kept (by last activity); older ones are removed when the 301st arrives. `feed.clear` removes resolved items only. A dismissed item is gone for good; new activity on the same thing (the same conversation, say) makes a **new** item, it does not bring the dismissed one back.
* **Resync after a reconnect.** There is no `since`. Reload with `feed.list {limit: 200}` (and `before` + `beforeId` for the rest, 300 at most) and `feed.summary`; the live events are only a convenience. A `ts` you already hold lets you stop paging early.
* **Encrypted messages in the feed.** The server cannot read `!` or `#urgent` in an envelope, so an encrypted message is **never** high priority: a direct message is `medium`, a group message `low`. The `title` is the sender's display name (direct) or the group's name; the `icon` is `chat` (direct) or `forum` (group); `count` coalescing works as for any message (the key is the conversation, not the text). The item has `e2e: true` and `message` is the **whole envelope** (`e2e1:…`, narrowed to the person's own boxes, never clipped): the app opens it with its own key. To open the conversation use `chatId` (`user-<username>` or `room-<group>`) and `chat` (`{scope, with|group}`); the web app passes no extra label.
* **`cards.list` and `feed.list` for an encrypted message.** The same: a card has `text` = the narrowed envelope and `e2e: true`.
* **For the "device added" item.** `category: security`, `actionType: none`, `chatId` absent, `ref: {deviceId}`; open the "Show your earlier messages on …?" offer for that device. There is no devices screen to send the person to.
* **`notifications_changed`, `card`, `notification` events.** They belong to the older four-badge layer (`cards.*`, `notifications.*`) and still fire next to the feed events. If you use only `feed.*` you may ignore all three.
* **Push.** Not built (no provider, no device-token action). A message push would carry no text.

## Message options (save, pin, unread, forward)

1. **Do `msg.save`, `msg.pin`, `conv.unread` work in encrypted chats? A real reply?** Yes. The server stores only message ids; a saved or pinned message comes back as the person's own **narrowed envelope** (`text: "e2e1:…"`, never plain text), which the device opens. Real replies: `docs/e2e-message-marks-replies.json` (`msg_save`, `msg_saved`, `msg_pin`, `msg_pins`, `conv_unread`, `conv_list`). Test: `connectum_e2e_marks_test`.
2. **Host channels: enforced, what error?** The server takes only `global`, `dm:<username>` and `group:<name>` as a conversation, so any other name (`host-…`, a workspace or an AI chat) is **`invalid`** with the words `id must be "global", "dm:<username>" or "group:<name>".`. Separately, pinning in the general room is `invalid` ("The general room has no pinned messages."); saving there is allowed. Other errors: `not_found`, `limit` (500 saved, 10 pinned), `rate_limited`.
3. **Forward: the wire form.** There is no flag and no quote: a forward is an **ordinary new message** whose text starts with `↪ [Forwarded by <name> • from <original author>]: ` followed by the original text (`forward.js`; the `• from …` part only when the author is someone else). The web app forwards the text (for an attachment it forwards the file name text, not the file). **From an encrypted chat into a plain one** nothing stops it: the device already holds the plain text and the message goes out as a plain message; the server cannot see it. Ask the person first, as the web app does not warn today.
4. **Edit and delete: only the author, what error?** Enforced by the server. A person who is not the author gets an event `edit_denied {messageId, reason}` or `delete_denied {messageId, reason}` with `reason: "forbidden"` (also `not_found`; for an edit `deleted` and `expired`, the edit window being `CHAT_EDIT_WINDOW_SEC`, 15 minutes by default). Real examples: `e2e-message-marks-replies.json` (`edit_denied`, `delete_denied`).
5. **32 or 38 vectors?** Neither was current: `message-format-vectors.json` has **41** sample messages. Both documents now say 41.

## Groups

1. **`cid` on `/creategroup` and `/addmember`, a create-with-members action, `owner` in the list, accepting an invitation:** built or already there, see the table above.
5. **Groups over 200 members cannot be encrypted: hard limit?** Yes, `MAX_GROUP_MEMBERS = 200`, enforced where the sender asks for the group's device keys: **`e2e.group_devices` answers `limit`** ("Groups of more than 200 people cannot use end-to-end encryption yet."). The app then cannot build an envelope. What happens to the send depends on the organisation's mode: in `optional` the server accepts a plain message (so the app must tell the person the group is **not** encrypted), in `required` the plain send is refused with `e2e_required`. An envelope may also not be wrapped for more than 250 devices (`too_long`).

# Branches in the join flow (3 November 2026)

The branch audit (`BRANCH_AUDIT.md`) is closed: every recommendation is built, tested and documented. For the mobile app:

1. **Send `connectBranch`** in `POST /api/sd/join` whenever the QR named a branch, and pre-fill the branch field with it **only when `GET /api/sd/enterprise/{id}` lists it in `branches`**. The server decides what to do with it: it is noted on the person; it becomes their branch when they picked none (always for an employee; for an outside person when their category has `branchFromScan` or `branchBound`); the approver sees it; with `routeByBranch` the approvers of that branch are asked first. A branch they picked themselves always wins. A scanned branch that does not exist or is switched off is not used, and the person still joins.
2. **A branch QR that cannot be used says so.** `connect.lookup`, `connect.scan` and `GET /api/sd/connect/{code}` answer with `enterprise.branchUnavailable: true` (and no `branch`) for a branch the organisation does not have or has switched off. The words on the web page are "That branch is not available. You can still join." Show the same and go on. An empty branch is no branch (no flag).
3. **A declined sign-up has a reason.** When the person tries to enter, `POST /api/sd/enter` answers `rejected` (HTTP 403) with "Your request to join was not approved. Reason: ..." (no reason: no second sentence). `GET /api/sd/me` has `rejectedReason` on the row of that organisation (`null` when none). The same text is emailed to them.
4. **If your app has the approver's screen:** a sign-up request carries `data.branch` and `data.connectBranch`; declining takes an optional `reason` (`req.respond {id, action: "reject", reason?}`, 500 characters at most, no "send again").
5. **Two new settings per category** (`admin.onboarding.save`, both off by default): `branchFromScan` and `routeByBranch`. Real replies: `docs/branch-join-replies.json`; Postman: the mobile collection, folder 9.
